## Disposition

**USEFUL FILE-ONLY DERIVED PROJECTION GENERATOR / IDENTITY AND CONTRACT VERIFICATION STILL OPEN**

The tranche has a good protected-effect boundary: it writes deterministic SQL/bundle files only and never connects to PostgreSQL. Its destructive SQL is confined to the dedicated derived schema `trek_projection_v0_1`.

The primary unresolved risk is the same trust-boundary defect already found in SQLite: the generator stamps an upstream `projection_hash` onto generated content without verifying that the JSONL files being encoded actually match that projection identity.

## Positive controls confirmed

- no PostgreSQL connection or execution exists in the generator;
- SQL rebuild scope is an explicit dedicated derived schema;
- generation order is deterministic;
- generated SQL uses one transaction;
- canonical record JSON is preserved as JSONB alongside indexed convenience columns;
- assertion projection status and partition are carried into generated SQL;
- source/provenance/reconciliation/relation rows are represented to the same current scope as the SQLite layer;
- apostrophes are escaped by doubling quotes;
- bundle identity hashes generated SQL text rather than PostgreSQL storage bytes;
- bundle records the upstream logical `projection_hash`;
- CI run 62 is green for current PostgreSQL tests and the inherited projection/diff/SQLite suites.

## Findings

### AUD-PG-001 — generated bundle pins an unverified logical projection identity

**Verdict:** CONFIRMED  
**Severity:** CRITICAL

`generate_sql()` reads `manifest.projection_hash` and places it into SQL metadata/comment output. `write_bundle()` copies the same value into the PostgreSQL bundle manifest.

The generator does not verify:
- `manifest.outputs` required files;
- JSONL per-file hashes/counts;
- recomputed upstream `projection_hash`;
- absence of stale/mixed canonical files.

The regression fixture demonstrates this directly: it writes `outputs: {}` plus arbitrary `sha256:projection-fixture`, then supplies independently created JSONL files. The generated SQL/bundle is considered valid and pinned to that arbitrary hash.

A deterministic SQL file can therefore be a perfectly reproducible encoding of logical content Y while claiming canonical projection X.

**Required correction:** reuse a single verified logical-projection bundle reader/validator shared with SQLite (or equivalent) before SQL generation. Reject missing/output-hash/count/projection-hash mismatches. Do not duplicate divergent trust logic across query backends.

---

### AUD-PG-002 — partition/status consistency is not enforced

**Verdict:** CONFIRMED  
**Severity:** CRITICAL

As in SQLite, source filename determines partition and row content supplies `projection_status`. The generated PostgreSQL table constrains only partition names, not status/partition correspondence.

A malformed input can generate:
- `partition='facts'`, `projection_status='UNRESOLVED'`;
- `partition='unresolved'`, `projection_status='STABLE'`.

The bundle would preserve the contradiction faithfully rather than fail closed.

**Required correction:** verify projection partition/status invariants before generation and encode compatible SQL CHECK constraints where useful as defense in depth.

---

### AUD-PG-003 — PostgreSQL bundle build provenance is incomplete

**Verdict:** CONFIRMED  
**Severity:** HIGH

The generated SQL copies upstream logical metadata including the logical `compiler_commit`, but the bundle manifest contains only:
- `bundle_version`;
- target schema name;
- upstream `projection_hash`;
- SQL hash/file.

It does not identify the PostgreSQL generator commit/version independently from the upstream logical compiler.

Different `build_postgres.py` versions can emit different SQL/schema/query behavior for the same canonical projection while producing bundle manifests with no exact generator identity.

**Required correction:** record query-bundle schema version plus generator/tool commit or content hash. Preserve upstream compiler identity separately.

---

### AUD-PG-004 — generated SQL input surface silently omits accepted assertion history

**Verdict:** SUPPORTED WITH CAVEAT  
**Severity:** HIGH unless explicitly versioned

PR #59 canonical projection includes `accepted_assertions.jsonl` and `accepted_reconciliation.jsonl` history exports. PR #71 imports reconciliation history but not accepted assertion history.

That may be an intentional query-surface choice, but the PostgreSQL bundle pins the full canonical projection hash while exposing only a subset of canonical outputs.

**Required resolution:** either materialize accepted assertion history or explicitly version/document the imported-output/query-surface contract in the bundle manifest. Consumers must be able to distinguish `derived query subset of projection X` from `complete materialization of projection X`.

---

### AUD-PG-005 — generated SQL bundle lacks canonical input receipt

**Verdict:** CONFIRMED  
**Severity:** HIGH

The bundle manifest hashes generated SQL but does not preserve the verified upstream `outputs` hash/count map or an equivalent import receipt.

Once upstream verification exists, the bundle should carry enough derivation receipt to audit exactly which canonical logical files were consumed without treating the generated SQL as a second source of truth.

---

### AUD-PG-006 — SQL textual safety depends on ambient PostgreSQL string-literal behavior

**Verdict:** SUPPORTED WITH CAVEAT  
**Severity:** MEDIUM

Single quotes are correctly doubled. JSON strings are canonicalized before quote escaping, which is directionally safe.

However the generated script does not establish session assumptions such as `standard_conforming_strings`. Modern PostgreSQL defaults to standard-conforming strings, but a rebuild bundle intended to be reproducible should not depend on mutable server/session configuration where textual literal interpretation could differ.

**Recommended correction:** use a deterministic literal encoding strategy whose behavior is explicit, or set/assert required session semantics at script start. Add fixtures containing backslashes, newlines/control escapes, Unicode, and SQL-looking payloads in text/JSON fields, not only apostrophes.

This is robustness/reproducibility, not evidence of a demonstrated injection exploit in the current file-only generator.

---

### AUD-PG-007 — projection contract validation should be centralized across SQLite/PostgreSQL

**Verdict:** CONFIRMED ARCHITECTURAL RECOMMENDATION  
**Severity:** HIGH

PR #68 and PR #71 independently parse logical projection directories and currently repeat the same trust omission.

If each backend grows its own bundle-verification, partition/status, required-output, and query-surface rules, drift is likely.

**Recommended resolution:** one deterministic canonical-projection reader/validator should establish:
- verified manifest/output identity;
- required output set;
- partition/status invariants;
- canonical rows;
- projection/query-surface receipt.

Backends should consume that verified representation rather than reinterpret raw directories independently.
